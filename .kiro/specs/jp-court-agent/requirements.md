# Requirements Document

## Introduction

The JP Court Agent is an AI-powered legal case management system that uses Elasticsearch as its persistent knowledge base and long-term memory. The system ingests, stores, and retrieves all documents relevant to a legal case — including crash reports, estimates, petitions, complaints, emails, letters, timelines, discrepancy reports, exhibits, summaries, analyses, insurer responses, TDI responses, and agent-generated documents — within a single unified index (`case_docs_index`). The AI agent performs hybrid search (BM25 + vector similarity) to retrieve relevant documents, generates new documents autonomously, and stores them back into Elasticsearch, creating a self-improving reasoning loop where every new document enriches future retrieval and analysis.

---

## Glossary

- **Agent**: The AI reasoning system that retrieves, analyzes, and generates legal case documents.
- **Case_Docs_Index**: The single unified Elasticsearch index (`case_docs_index`) that stores all documents for all legal cases.
- **Document**: A structured record stored in the Case_Docs_Index containing metadata, full text, and a vector embedding.
- **Edges**: A list of relationships stored within a document, connecting it to other `doc_id`s with a specific `relation_type` (e.g., `supports`, `contradicts`).
- **Embedding**: A 768-dimensional dense vector representation of a document's text generated by `all-mpnet-base-v2` (SentenceTransformer), used for semantic similarity search.
- **Hybrid_Search**: The default retrieval strategy combining BM25 keyword scoring (weight 0.3) and cosine kNN vector similarity (weight 0.7, 768-dim, num_candidates=50) to rank documents. Produces confidence-weighted scores that reflect legal relevance hierarchy.
- **BM25_Search**: An on-demand retrieval mode using pure keyword matching. Used when the user explicitly requests it, when debugging retrieval, or when exact section/citation lookup is needed.
- **Search_Mode**: The active retrieval strategy for a given query. Options: `hybrid`, `bm25`, or `graph`.
- **Doc_Ingest**: The Python tool (`ingest_doc.py`) responsible for generating 768-dim embeddings via `all-mpnet-base-v2` and inserting documents into the Case_Docs_Index.
- **Query_ES**: The Python tool (`query_es.py`) responsible for executing hybrid kNN+BM25 search queries against the Case_Docs_Index. Accepts a `search_mode` parameter (`hybrid` or `bm25`).
- **Embedding_Tool**: The `all-mpnet-base-v2` SentenceTransformer model responsible for generating 768-dimensional vector embeddings from text.
- **Local_Capability**: The requirement to use local Python scripts and libraries (`elasticsearch`, `sentence-transformers`) to execute core logic, ensuring full control over parameters and models.
- **Document_Type**: A classification label for a document. Valid values: `crash_report`, `estimate`, `petition`, `complaint`, `email`, `letter`, `timeline`, `discrepancy_report`, `exhibit`, `summary`, `analysis`, `insurer_response`, `tdi_response`, `agent_generated`.
- **Argument_Graph**: A structured reasoning object containing `procedural`, `liability`, `damages`, `contradiction`, and `exhibit` chains, built via recursive graph expansion.
- **Fact_Verification_Layer**: A safety mechanism that validates factual assertions against the Argument_Graph to identify "supported" vs "unsupported" claims.
- **Case_ID**: A unique identifier that groups all documents belonging to the same legal case.
- **Doc_ID**: A unique identifier for a single document within the Case_Docs_Index.
- **Self_Improving_Loop**: The process by which every document the Agent generates and stores enriches the knowledge base, improving the quality of future retrievals and reasoning.

## Requirements

### Requirement 0: Local Execution Priority

1. THE Agent SHALL use Local_Capability (Python scripts) for all document ingestion, hybrid search, and graph traversal operations to ensure the correct application of local `all-mpnet-base-v2` embeddings and multi-hop retrieval logic.
2. THE Agent SHALL use the `elasticsearch` MCP tool directly for pure BM25 search operations ONLY for non-analytical metadata verification.
3. THE Agent SHALL execute analytical retrieval via the "Man-in-the-middle" protocol: The Agent generates a local Python search script, the user executes it locally, and the user provides the high-signal hits back to the Agent.
4. THE Agent SHALL NOT perform "Reasoning-as-Retrieval" (evaluating logic over a bulk dump of BM25 keywords) to prevent context noise and loss of precision.
5. THE Agent SHALL provide a universal standalone script (`get_embedding.py`) that accepts an input string and outputs a 768-dim JSON vector for use in the "Man-in-the-middle" flow.

### Requirement 1: Unified Document Storage

**User Story:** As a legal professional, I want all case-related documents stored in a single searchable index, so that the AI agent can access the full case history from one place.

#### Acceptance Criteria

1. THE Case_Docs_Index SHALL store documents of all fourteen supported Document_Types: `crash_report`, `estimate`, `petition`, `complaint`, `email`, `letter`, `timeline`, `discrepancy_report`, `exhibit`, `summary`, `analysis`, `insurer_response`, `tdi_response`, and `agent_generated`.
2. WHEN a document is stored in the Case_Docs_Index, THE Case_Docs_Index SHALL require the following fields to be present: `doc_id`, `case_id`, `type`, `title`, `text`, `date`, `tags`, `embedding`, and `edges`.
3. THE `edges` field SHALL be a list of objects, each containing a `target` (Doc_ID) and a `relation` (Relation_Type). VALID Relation_Types are: `supports`, `contradicts`, `timeline_precedes`, `timeline_follows`, `is_evidence_for`, `is_related_to`.
4. IF a document submitted for storage is missing any required field, contains an invalid `type`, an invalid `Relation_Type`, or an `embedding` that does not have exactly 768 dimensions, THEN THE Doc_Ingest SHALL reject the document.
4. THE Case_Docs_Index SHALL store the `embedding` field as a dense vector of exactly 768 dimensions using cosine similarity as the distance metric.
5. WHEN a document is stored, THE Case_Docs_Index SHALL index the `type` field as a keyword to enable exact-match filtering by Document_Type.
6. WHEN a document is stored, THE Case_Docs_Index SHALL index the `case_id` field as a keyword to enable exact-match filtering by Case_ID.
7. IF a document is submitted to Doc_Ingest with a `doc_id` that already exists in the Case_Docs_Index, THEN THE Doc_Ingest SHALL reject the submission, return an error indicating the duplicate `doc_id`, and leave the existing document unchanged.
8. THE Agent SHALL permit partial updates to existing documents for the sole purpose of modifying the `edges` or `tags` fields, provided the original `text` and `embedding` are preserved (Surgical Update Property).

### Requirement 2: Document Ingestion and Embedding

**User Story:** As a legal professional, I want to ingest documents into the system with automatic embedding generation, so that documents are immediately available for both keyword and semantic search.

#### Acceptance Criteria

1. WHEN a document is submitted to Doc_Ingest, THE Doc_Ingest SHALL invoke the Embedding_Tool (`all-mpnet-base-v2`) to generate a 768-dimensional vector embedding from the document's `text` field before storing the document.
2. WHEN the Embedding_Tool is invoked with a non-empty text string of up to 8192 tokens, THE Embedding_Tool SHALL return a vector of exactly 768 floating-point values.
3. IF the actual vector returned by the Embedding_Tool has a dimension other than 768, THEN THE Doc_Ingest SHALL reject the document and return an error indicating the embedding dimension mismatch, regardless of any dimension metadata accompanying the vector.
4. WHEN Doc_Ingest successfully stores a document, THE Doc_Ingest SHALL return the assigned `doc_id` of the stored document.
5. THE Doc_Ingest SHALL assign a unique `doc_id` to each document such that no two documents in the Case_Docs_Index share the same `doc_id`.
6. THE Doc_Ingest SHALL store documents such that retrieving a document by its `doc_id` returns values for all submitted fields (`doc_id`, `case_id`, `type`, `title`, `text`, `date`, `tags`) that are identical to those submitted, excluding the `embedding` field which is generated internally (round-trip property).
7. IF a document submitted to Doc_Ingest has a missing or empty `text` field, THEN THE Doc_Ingest SHALL reject the document and return a validation error without invoking the Embedding_Tool.
8. IF the Embedding_Tool fails or is unavailable when Doc_Ingest attempts to generate an embedding, THEN THE Doc_Ingest SHALL abort the ingestion, return an error indicating the embedding failure, and not store any partial document in the Case_Docs_Index.

### Requirement 3: Hybrid Search Retrieval (Default Mode)

**User Story:** As an AI agent, I want to retrieve the most relevant documents for a given query using both keyword and semantic signals by default, so that I can reason over the most pertinent case evidence with confidence-weighted scores.

#### Acceptance Criteria

1. WHEN Query_ES is invoked with a query string and a Case_ID, THE Query_ES SHALL by default execute a hybrid search.
2. WHEN `search_mode=graph` is invoked, THE Query_ES SHALL: (a) Execute a standard hybrid search to identify "seed" documents, (b) Perform a Breadth-First Search (BFS) expansion to retrieve all documents linked to those seeds via the `edges.target` field up to a depth of 50 nodes, and (c) Return the combined, de-duplicated set of documents categorized into Argument_Graph chains.
2. WHEN Query_ES is invoked, THE Query_ES SHALL generate a 768-dim query embedding from the query string using the Embedding_Tool before executing the vector similarity component of the hybrid search.
3. WHEN Query_ES is invoked with a Case_ID filter, THE Query_ES SHALL return only documents whose `case_id` matches the specified Case_ID.
4. WHEN Query_ES executes a hybrid search, THE Query_ES SHALL return results ordered by descending hybrid relevance score.
5. WHEN Query_ES is invoked with a Document_Type filter, THE Query_ES SHALL return only documents whose `type` matches the specified Document_Type. IF the provided Document_Type value is not one of the fourteen supported Document_Types, THEN THE Query_ES SHALL return a validation error identifying the invalid type value.
6. IF Query_ES is invoked with a query string that produces no matching documents, THEN THE Query_ES SHALL return an empty result set without raising an error.
7. WHEN Query_ES is invoked, THE Query_ES SHALL accept an optional `top_k` parameter specifying the maximum number of results to return, defaulting to 10 when not provided, and accepting values between 1 and 100 inclusive.
8. IF the Embedding_Tool fails or is unavailable when Query_ES attempts to generate a query embedding in hybrid mode, THEN THE Query_ES SHALL automatically fall back to BM25-only search, log a warning indicating the fallback, and proceed without returning an error.
9. WHEN Query_ES returns results, each result SHALL include at minimum the fields `doc_id`, `case_id`, `type`, `title`, `text`, `date`, `tags`, a `score` field containing the relevance score, and a `search_mode` field indicating whether results were produced by `hybrid` or `bm25` retrieval.
10. WHEN `search_mode=bm25` is used, the Agent SHALL execute the query directly via the `elasticsearch` MCP tool for efficiency, bypassing Python script generation and query embedding.
11. THE Agent SHALL use `search_mode=bm25` when: (a) the user explicitly requests keyword/BM25/exact-match search, (b) the Embedding_Tool is unavailable, or (c) the Agent is performing a non-analytical metadata check.

### Requirement 4: Agent-Generated Document Creation

**User Story:** As an AI agent, I want to generate new documents (discrepancy reports, timelines, summaries, exhibits) and store them back into the knowledge base, so that my analysis becomes part of the persistent case record.

#### Acceptance Criteria

1. WHEN the Agent generates a new document of type `discrepancy_report`, `timeline`, `summary`, `analysis`, `exhibit`, `line_of_defense`, or `trial_brief`, THE Agent SHALL set the `type` field to `agent_generated` in the document submitted to Doc_Ingest.
2. WHEN the Agent stores a generated document, THE Agent SHALL populate all required fields (`doc_id`, `case_id`, `type`, `title`, `text`, `date`, `tags`) before invoking Doc_Ingest, with `embedding` generated by Doc_Ingest as defined in Requirement 2.
3. WHEN the Agent stores a generated document, THE Agent SHALL set the `date` field to the current date and time in ISO 8601 format with a UTC offset (e.g., `2026-05-28T14:30:00+00:00`).
4. WHEN the Agent stores a generated document, THE Agent SHALL include at least one tag in the `tags` field that is a non-empty string of 1–100 characters describing the document's subject matter, and SHALL include a tag identifying the content subtype (e.g., `discrepancy_report`, `timeline`, `summary`, `analysis`, or `exhibit`) to preserve discoverability after the `type` field is set to `agent_generated`.
5. THE Agent SHALL execute the Fact_Verification_Layer for every factual assertion in a generated document; IF a claim is found to be "unsupported" by the Argument_Graph, THE Agent SHALL annotate, rewrite, or remove the claim before storage.
5. THE Agent SHALL allow the generation of local Markdown (`.md`) versions of agent-generated documents to facilitate external review and courtroom use.

---

### Requirement 5: Self-Improving Knowledge Loop

**User Story:** As an AI agent, I want every document I generate to improve the quality of future retrievals, so that the system's reasoning capability grows with each case interaction.

#### Acceptance Criteria

1. WHEN a new document is stored in the Case_Docs_Index, THE Case_Docs_Index SHALL make the document available for retrieval by subsequent Query_ES calls within 1 second of the Doc_Ingest call returning success, without requiring a manual index refresh.
2. WHEN a reasoning step begins, THE Agent SHALL invoke Query_ES with a query string derived from the current task context and retrieve at least the top 10 documents before generating a response or new document.
3. WHEN the Agent retrieves documents for a reasoning step, THE Agent SHALL include documents of type `agent_generated` in the candidate result set alongside all other Document_Types.
4. IF the Case_Docs_Index contains at least 5 documents for the relevant Case_ID and the Agent has stored a generated document, THEN a Query_ES hybrid search using the stored document's `title` as the query string SHALL return that document within the top 5 results (Self_Improving_Loop verification property).
5. IF Query_ES returns zero results for the query used at the start of a reasoning step, THEN THE Agent SHALL log a warning indicating that no context documents were found and proceed with the reasoning step using only the current task input.

---

### Requirement 6: Document Filtering and Case Isolation

**User Story:** As a legal professional, I want to ensure that queries for one case never return documents from another case, so that case data remains isolated and confidential.

#### Acceptance Criteria

1. WHEN Query_ES is invoked with a Case_ID, THE Query_ES SHALL apply the Case_ID as a mandatory filter such that the result set contains zero documents whose `case_id` differs from the specified Case_ID.
2. WHEN Query_ES is invoked with a Case_ID and the Case_Docs_Index contains documents from multiple cases, THE Query_ES SHALL return only documents whose `case_id` exactly matches the specified Case_ID, with zero documents from any other case present in the result set.
3. WHEN Query_ES is invoked without a Case_ID, THE Query_ES SHALL return a validation error indicating that Case_ID is required, return zero documents, and execute no search query against the Case_Docs_Index.
4. THE Case_Docs_Index SHALL accept a Case_ID value that is a non-empty string of 1–64 characters containing only alphanumeric characters, hyphens, and underscores; IF a Case_ID value outside this format is provided to Query_ES or Doc_Ingest, THEN the tool SHALL return a validation error identifying the invalid Case_ID format.

---

### Requirement 7: Embedding Round-Trip Consistency

**User Story:** As a developer, I want the embedding pipeline to produce consistent, stable vectors, so that documents indexed at different times remain comparable during hybrid search.

#### Acceptance Criteria

1. WHEN the Embedding_Tool is invoked twice with the same input text, THE Embedding_Tool SHALL return vectors whose cosine similarity is 1.0 (deterministic embedding property).
2. WHEN the Embedding_Tool is invoked with a non-empty text string of up to 8192 tokens, THE Embedding_Tool SHALL return a valid 768-dimensional embedding without truncation errors.
3. IF the Embedding_Tool is invoked with a text string exceeding 8192 tokens, THEN THE Embedding_Tool SHALL return an error indicating that the input exceeds the maximum token limit, without returning a partial or truncated embedding.
4. IF the Embedding_Tool is invoked with an empty string, THEN THE Embedding_Tool SHALL return an error indicating that empty text cannot be embedded.
5. WHEN Doc_Ingest stores an embedding vector produced by the Embedding_Tool, THE Doc_Ingest SHALL preserve the vector such that the cosine similarity between the original vector and the stored-then-retrieved vector is ≥ 0.9999, permitting format conversions (e.g., float64 to float32) that do not reduce cosine similarity below this threshold.

---

### Requirement 8: Search Mode Selection

**User Story:** As a legal professional or AI agent, I want the system to use hybrid search by default and switch to keyword-only search when I explicitly ask or when the situation demands precision over semantics, so that retrieval is always appropriate to the task.

#### Acceptance Criteria

1. THE Agent SHALL default to `search_mode=hybrid` for all retrieval operations unless explicitly overridden.
2. WHEN the user's request contains any of the following signals, THE Agent SHALL switch to `search_mode=bm25`: phrases such as "keyword search", "BM25", "exact match", "exact term", "BM25 only", "keyword only", "run keyword search", or "run BM25".
3. WHEN the user's request is a verbatim statute or rule citation lookup, THE Agent SHALL use the "Man-in-the-middle" protocol to ensure correct sub-provision prioritization via local `all-mpnet-base-v2` embeddings.
4. THE Agent SHALL NOT attempt to simulate semantic ranking over BM25 results within its own reasoning context.
5. WHEN `search_mode=bm25` is active, THE Agent SHALL annotate the response with: `[BM25-only retrieval — semantic ranking not applied]`. IF the switch was an automatic fallback, THE Agent SHALL use: `[BM25 fallback — Embedding_Tool unavailable, hybrid not executed]`.
6. WHEN `search_mode=hybrid` is active, THE Agent SHALL annotate the response with the model and weights used: `[Hybrid kNN+BM25 — all-mpnet-base-v2 768-dim, 0.7 cosine / 0.3 BM25]`.
7. IF the Embedding_Tool is unavailable during a hybrid retrieval attempt, THE Agent SHALL fall back to `search_mode=bm25` automatically, log a warning in the response, and NOT abort the retrieval.
8. WHEN the user requests "run hybrid search" or "use hybrid", THE Agent SHALL confirm and execute `search_mode=hybrid` regardless of any prior session context.
9. THE Agent SHALL maintain a `DEBUG_EXPLAIN_QUERIES` feature flag (default: `True`) in its analytical scripts.
10. WHEN `DEBUG_EXPLAIN_QUERIES` is `True`, THE Agent SHALL print an explanation of its query selection, the search mode (BM25, Hybrid, or Graph), and the full Elasticsearch DSL query body to the standard output for debugging purposes.
